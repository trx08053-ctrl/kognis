# Эволюция: данные, контракты, архитектура

Когда в TASK (раздел 2a) изменения данных, публичных интерфейсов или границ модулей — «да»,
заполняется раздел 2b по этому руководству. Для остальных задач документ не нужен.

## Изменение данных (схема или смысл)
1. **Версии:** исходная и целевая версия схемы (номер миграции).
2. **Преобразование:** что происходит с существующими записями (заполнение, перенос, пересчёт).
3. **Совместимость на время обновления:** expand → migrate → contract. Сначала добавить совместимо
   (старая версия приложения работает с новой схемой), выкатить код, перенести данные, удалять старое —
   в следующем релизе.
4. **Проверка на данных прошлой версии:** тест `@pytest.mark.migration` поднимает БД в схеме прошлого
   релиза с репрезентативными данными (фикстура `tests/migrations/<версия>/`), применяет миграцию и
   проверяет данные. Проверка на пустой базе не считается.
5. **Восстановление:** откат (если преобразование обратимо) **или** исправление с продолжением миграции.
   Необратимое не объявлять обратимым: тогда — бэкап перед миграцией и проверенная процедура восстановления
   в `docs/RUNBOOK.md`. Запуск на проде — решение человека.

## Изменение публичного интерфейса (API модуля, контракт `docs/contracts/`, CLI)
- **Потребители:** какие модули и внешние системы затронуты (`just context <модуль>` → «используется модулями»).
- **Совместимость:** совместимое (добавление) или ломающее. Ломающее обозначается явно (`feat!:` в коммите,
  MAJOR-версия для внешних контрактов) и требует решения человека.
- **Переходный период:** старое и новое работают вместе; старое помечено устаревшим и удаляется не раньше
  следующего релиза.

## Пересмотр границ модулей
Через ADR: **проблема → варианты → решение → переход → проверка результата**. После принятия ADR в той же
задаче обновляются `.importlinter`, ARCHITECTURE.md и карточки модулей — проверки должны отражать новое решение.
Устаревшее ограничение не обходится, а меняется этим процессом.

## Временное архитектурное исключение
Например, модуль читает таблицу соседа напрямую ради производительности. Оформляется ADR с разделом
`## Исключение`, в котором обязательны:
- **Причина:** почему нельзя по правилам сейчас;
- **Ответственный:** роль, которая следит и снимет исключение;
- **Пересмотр:** условие или дата, когда исключение пересматривается.
`just check refs` не пропустит ADR с «Исключением» без этих трёх полей.
