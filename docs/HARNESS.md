# План развёртывания harness-окружения для агентной разработки

> Версия плана: 1.0 · 2026-09-22 · хост: DGX Spark (ARM64, Ubuntu 24.04)
> Основной агент: Claude Code (Opus). Дополнительная модель: локальный Qwen3.5-122B (vLLM, :8000) для дешёвых подзадач и перекрёстного ревью.

## 0. Главная идея

Агент надёжен ровно настолько, насколько надёжно окружение вокруг него. Поэтому правила, состояние и проверки
лежат **в репозитории**, а не в памяти модели. Механизмы должны работать принудительно (hooks, CI, pre-commit),
а не только «по договорённости» в промпте. Каждое утверждение «готово» должно опираться на **доказательство**,
привязанное к конкретному состоянию кода.

Пять опор:

1. **Правила** — короткий `AGENTS.md` и ссылки на подробные документы (progressive disclosure: агент читает детали только когда нужно).
2. **Состояние** — задачи, граф зависимостей, прогресс и блокеры хранятся в git (переживают прерывание и смену сессии).
3. **Навигация** — карта проекта, карточки модулей, поиск по символам (LSP), индексы с проверкой свежести.
4. **Проверки** — единая команда `just verify`, которую агент не может ослабить; отдельное ревью в чистом контексте.
5. **Границы** — песочница, deny-правила, секреты вне досягаемости, журнал действий и затрат, список решений только для человека.

Файлы в этой папке:

| Файл | Назначение |
|---|---|
| `PLAN.md` | этот план |
| `template/AGENTS.md` | правила работы агента (шаблон для каждого проекта) |
| `template/CLAUDE.md` | точка входа Claude Code, импортирует `AGENTS.md` |
| `template/docs/templates/TASK.md` | шаблон постановки задачи с гипотезами и экспериментами |
| `template/docs/adr/0000-template.md` | шаблон ADR (MADR) |
| `template/docs/templates/MODULE_CARD.md` | шаблон карточки модуля |
| `evals/README.md` | контрольные задачи для оценки harness |

## 2. Масштабирование по размеру проекта

Сложность — соразмерно проекту. Copier-шаблон спрашивает профиль при создании.

| Профиль | Когда | Что включено |
|---|---|---|
| **S — скрипт/утилита** | < 2k строк, один модуль | AGENTS.md, justfile, lint+types+tests, lefthook, conventional commits, `tasks/` вместо Beads |
| **M — сервис/приложение** | 2–50k строк, 3–15 модулей | + карта проекта и карточки модулей, import-linter/dependency-cruiser, ADR, Beads, контракты, evidence-файлы, reviewer-subagent, релизы |
| **L — продукт/монорепо** | > 50k строк, несколько команд/агентов | + Serena/семантический индекс, e2e, мутационные тесты критичного ядра, merge queue, OTel→Langfuse, бюджеты, Renovate, SBOM |

Правило: элемент harness добавляется, когда без него случилась (или вот-вот случится) реальная ошибка.

## 4. Правила работы (AGENTS.md)

Готовый шаблон: `template/AGENTS.md`. Принципы:

- **Коротко.** Подробности — ссылками. Каждое правило проверяемо или применяется принудительно.
- **Цикл работы:** понять → найти контекст → план → маленький шаг → verify → коммит → обновить состояние → следующий шаг.
- **Команды** — только через `just`, чтобы агент, человек и CI выполняли одно и то же.
- **Запреты** явные: не ослаблять проверки, не трогать защищённые файлы, не читать секреты, не делать push/release/миграции прода без человека.
- `CLAUDE.md` содержит только `@AGENTS.md` и специфику Claude Code (subagents, skills), чтобы проект оставался совместим с другими агентами.

## 5. Постановка задач

Шаблон: `template/docs/templates/TASK.md`. Разделы: цель (зачем, а не только что), границы (in/out of scope),
критерии приёмки (проверяемые, лучше в виде тестов или команд), ограничения, риски, **неизвестные → гипотезы → эксперименты**.

Работа с неопределённостью:

1. Каждое существенное «неизвестно» формулируется как гипотеза с критерием опровержения:
   «Библиотека X выдерживает 1k rps на Spark; опровергается, если p95 > 50 мс в бенчмарке `bench/x.py`».
2. Эксперимент — это **spike** с таймбоксом (например, ≤ 30 минут или ≤ N $), в отдельной ветке или worktree, код выбрасывается.
3. Итог фиксируется в TASK.md (подтверждено/опровергнуто + данные). Если итог влияет на архитектуру, пишется ADR.
4. Пока критичные гипотезы не проверены, основную реализацию не начинаем.

Задачи классифицируются: **trivial** (сразу делать) / **standard** (TASK.md + план) / **risky** (TASK.md + гипотезы + человек утверждает план).

## 6. Архитектура

### 6.1 Описание
`docs/ARCHITECTURE.md` содержит:
- контекстную диаграмму (Mermaid C4-level 1–2);
- таблицу модулей: имя, ответственность (одно предложение), публичный интерфейс, владелец, допустимые зависимости;
- слои (например, `api → app → domain ← infra`; domain ни от чего не зависит);
- правила: межмодульные вызовы только через публичный интерфейс (`module/__init__.py` / `index.ts`), без импорта внутренностей.

### 6.2 Автоматическая проверка границ
Python — `import-linter` (`.importlinter`):
```ini
[importlinter]
root_package = app
[importlinter:contract:layers]
name = Layered architecture
type = layers
layers = app.api | app.services | app.domain
[importlinter:contract:domain-pure]
name = Domain has no infra deps
type = forbidden
source_modules = app.domain
forbidden_modules = app.infra, sqlalchemy, httpx
```
TypeScript — `dependency-cruiser` (`.dependency-cruiser.cjs`, правила `forbidden`, запрет циклов и `no-orphans`).
Дополнительно — ast-grep-правила для паттернов, которые линтеры не ловят (например, «SQL только в `infra/db`»).
Команда `just arch` входит в `just verify`. Нарушение блокирует коммит и CI.

### 6.3 ADR
- Формат MADR: контекст → варианты (≥ 2) → решение → обоснование → последствия (плюсы/минусы/что станет сложнее) → статус.
- ADR пишется, когда решение дорого отменить: выбор хранилища, протокола, фреймворка, границы модулей, формат данных, политика совместимости.
- ADR неизменяемы: изменение решения оформляется новым ADR со статусом `Supersedes NNNN`.
- Агент может **предложить** ADR (`Proposed`); статус `Accepted` ставит человек.

## 7. Планирование и исполнение

### 7.1 Декомпозиция
- Задача → план из шагов, каждый шаг ≤ ~200–300 строк diff, с понятной проверкой («тест X зелёный», «команда Y выводит Z»).
- Шаги оформляются задачами Beads с зависимостями: `bd create "…" --deps blocks:bd-12`; `bd ready` показывает, что можно брать.
- Каждый шаг — отдельный коммит (Conventional Commits) после зелёного `just verify`.

### 7.2 Состояние и продолжение после прерывания
Источник правды — **файлы в git**, не контекст модели:
- `bd` — статус задач (open / in_progress / blocked / done), блокеры, заметки;
- `tasks/<id>/PROGRESS.md` — журнал: что сделано, последнее доказательство, **следующий шаг**, открытые вопросы;
- коммиты — точки восстановления (плюс встроенные чекпоинты Claude Code `/rewind`).

Протокол:
- **Старт сессии** (SessionStart hook выводит): `git status`, `bd ready`, последние 20 строк активного `PROGRESS.md`.
- **После каждого шага**: обновить PROGRESS.md и `bd`, закоммитить.
- **Перед компактизацией / остановкой** (PreCompact/Stop hook): напомнить записать «следующий шаг».
- Длинные задачи — `just agent-run --task <id>` (`scripts/agent_run.py`): цикл «новая сессия `claude -p` на чистом контексте → состояние из git/bd/PROGRESS.md», пока задача не закрыта/заблокирована или не сработал лимит.

### 7.3 Лимиты повторов и расходов
| Лимит | Значение по умолчанию | Механизм |
|---|---|---|
| Попытки починить одну и ту же проверку | 3 → затем стоп и эскалация с диагнозом | `verify.py` считает падения подряд → `ESCALATE`; `just task-block` |
| Длительность сессии | 30 мин (`--session-timeout`) | `agent_run.py` убивает группу процессов; работа сохранена в git/PROGRESS |
| Сессий без прогресса подряд | 2 (`--max-idle`) — нет новых коммитов и изменений PROGRESS.md → стоп, нужен человек | `agent_run.py` |
| Бюджет | на сессию `--max-budget-usd` (2 $), на задачу `--total-budget` (6 $ standard / 20 $ risky); сессия, убитая по таймауту, считается по верхней границе | флаг CLI + `agent_run.py`, журнал `.agent-log/runs.jsonl` |
| Время на spike | 30 мин | TASK.md |
| Параллельных агентов | ≤ 3–4 worktree | договорённость + скрипт |
Дешёвые массовые операции (классификация, суммаризация логов, черновые ревью) отдаются локальному Qwen через OpenAI-совместимый API :8000 — бесплатно по токенам.

### 7.4 Роли (subagents в `.claude/agents/`)
- **explorer** — только чтение, ищет контекст, возвращает ссылки `file:line` и выводы, а не содержимое файлов;
- **planner** — делает TASK.md/план, гипотезы, зависимости; кода не пишет;
- **implementer** — один шаг плана за раз;
- **reviewer** — чистый контекст, видит только diff + TASK.md + ARCHITECTURE; не может редактировать файлы.

## 8. Навигация и контекст

### 8.1 Карта проекта и карточки модулей
- `docs/MAP.md` — **генерируется** скриптом `just map`: дерево модулей, публичные символы (через ast-grep/ctags), точки входа, тесты по модулю. Руками пишется только верхний абзац.
- `docs/modules/<name>.md` (шаблон `MODULE_CARD.md`): назначение, публичный API со ссылками `path#symbol`, контракты, инварианты, зависимости (входящие/исходящие), тесты, известные проблемы.

### 8.2 Порядок поиска (от точного к нечёткому)
1. `MAP.md` → карточка модуля → нужные файлы.
2. Символы: Serena `find_symbol` / `find_referencing_symbols`, LSP go-to-definition.
3. Текст: `rg -n`, структура: `ast-grep -p 'def $F($$$)'`.
4. Семантика (только профиль L или незнакомая кодовая база): векторный индекс в Qdrant, переиндексация по git-хуку post-commit.
5. Внешние доки: Context7 MCP по точной версии из lock-файла.

### 8.3 Экономия контекста
- Читать фрагменты (`Read` с offset/limit, `get_symbols_overview`), а не целые файлы.
- Расширять по зависимостям: символ → его вызовы/вызывающие → контракт → тест.
- Широкий поиск отдавать subagent `explorer`, чтобы в основной контекст попал только вывод.

### 8.4 Свежесть ссылок и индексов
`just docs-check` (в verify и CI):
- `lychee --offline docs/` — ссылки на файлы и якоря;
- скрипт `check_refs.py` — каждая ссылка `path#symbol` в карточках существует в текущем коде (через ast-grep);
- `just map && git diff --exit-code docs/MAP.md docs/generated/` — сгенерированное совпадает с кодом;
- семантический индекс хранит commit-sha; при несовпадении с HEAD — переиндексация или предупреждение.

| Безопасность | gitleaks, semgrep, osv-scanner | pre-commit (gitleaks), CI |
| Документация | lychee, check_refs, генерация без diff | verify |
| Качество тестов (выборочно) | mutmut / Stryker по ядру домена | nightly |
| Покрытие изменений | diff-cover ≥ 80 % на новые строки | CI |

### 9.2 Доказательство «готово»
`just verify` пишет `.evidence/<tree-hash>.json`:
```json
{"tree": "<git write-tree>", "head": "<sha>", "dirty": false,
 "checks": [{"name":"types","cmd":"basedpyright","exit":0,"duration_s":12.4}, ...],
 "ts": "2026-09-22T20:00:00Z", "tool_versions": {"python":"3.12.3", ...}}
```
- Задача может перейти в `done`, только если есть evidence для **текущего** tree-hash со всеми `exit: 0`
  (Stop-hook `require-evidence.sh` и CI проверяют это; при изменении кода после verify доказательство устаревает автоматически).
- В финальном сообщении/PR агент приводит: sha, список проверок, ссылку на evidence, что проверено вручную и что **не** проверено.

### 9.3 Защита от ослабления проверок
- **Защищённые файлы** (конфиги линтеров/типов/архитектуры, `justfile` verify, CI, `lefthook.yml`, `.claude/settings.json`, существующие тесты-оракулы): PreToolUse-hook `guard-protected.sh` блокирует правку и требует подтверждения человека.
- ast-grep/grep-правило в CI запрещает новые `# type: ignore`, `noqa`, `eslint-disable`, `@ts-expect-error`, `pytest.skip`, `.only`, `xfail` без ссылки на задачу (`# noqa: E501  # bd-42`).
- **Ratchet**: пороги покрытия/количество предупреждений могут только улучшаться (сравнение с `main`).
- Удаление/изменение утверждений в тестах в одном diff с изменением кода — флаг для reviewer.
- CI — источник истины: локальная зелень без CI не считается.

### 9.4 Отдельный этап ревью
1. **Самопроверка** implementer: diff против критериев приёмки TASK.md.
2. **Reviewer-subagent** в чистом контексте, чеклист: корректность, границы модулей, безопасность, тесты проверяют поведение (а не реализацию), нет ли ослабления проверок, обновлены ли доки/ADR, совместимость.
3. **Перекрёстное ревью** другой моделью (локальный Qwen или `/code-review`) — для risky-задач.
4. **Человек** — merge в main для risky-задач, всё из раздела 12.

## 11. Версии и релизы

### 11.1 Git-процесс
- **Trunk-based**: короткие ветки `feat/bd-42-slug`, живут ≤ 1–2 дня; `main` всегда зелёный и защищён.
- Conventional Commits (commitlint в `commit-msg`), атомарные коммиты, squash или rebase-merge.
- Агент коммитит локально свободно; **push, merge в main, теги — по решению человека** (или по явному разрешению на задачу).

### 11.2 Параллельная работа
- Каждый агент — свой **git worktree** (`claude --worktree` / `git worktree add ../proj-bd-42 -b feat/bd-42`), своя задача Beads, свои порты/БД (переменная `WORKTREE_ID` → смещение портов, отдельная схема БД или testcontainers).
- Перед merge: `just integrate` — rebase ветки на свежий main, `just verify` на **объединённом** результате. При нескольких ветках — последовательное слияние во временную ветку `integration/*` и полный прогон (или merge queue на форже).
- Конфликты в общих файлах (MAP.md, CHANGELOG) не решаются вручную — они генерируются заново.

### 11.3 Воспроизводимая сборка
- Все lock-файлы в git (`uv.lock`, `pnpm-lock.yaml`, `mise.lock`), образы Docker по digest, `SOURCE_DATE_EPOCH` из коммита.
- `just build` в devcontainer = та же команда в CI. Для релизов — SBOM (syft) и подпись артефактов (cosign) на профиле L.

### 11.4 Версионирование и совместимость
- SemVer. MAJOR — ломающие изменения публичных контрактов (API, CLI, формат данных, конфиг).
- Совместимость: N-1 для API и схем данных; удаление — через deprecation (предупреждение ≥ 1 минорный релиз).
- Проверка ломающих изменений в CI: oasdiff (OpenAPI), buf breaking (protobuf), тесты совместимости со старыми фикстурами данных.
- Релиз: release-please (или `git cliff --bump`) → PR с версией и CHANGELOG → человек подтверждает → тег → сборка.

### 11.5 Миграции и восстановление
- Миграции схемы (Alembic / Atlas / Prisma migrate) по принципу **expand → migrate → contract**: сначала добавить совместимо, затем перенести данные, удалить старое только в следующем релизе.
- Каждая миграция имеет тест up/down на копии данных (testcontainers).
- Перед миграцией прода — бэкап и проверенная команда отката в RUNBOOK. Запуск миграций на проде — только человек.
- Восстановление: откат релиза = деплой предыдущего тега; данные — из бэкапа (restic/pgBackRest), учения по восстановлению раз в квартал.

## 12. Инструменты, права, безопасность, наблюдаемость

### 12.1 Воспроизводимое окружение
Devcontainer (Docker) с mise; агент в режиме автономной работы запускается внутри контейнера или со встроенным sandbox Claude Code (ограничение файловой системы и сети). На хосте DGX Spark — не давать агенту доступ к чужим сервисам/данным без необходимости.

### 12.2 Ограниченные права (`.claude/settings.json`)
```json
{
  "permissions": {
    "allow": ["Bash(just:*)", "Bash(git status:*)", "Bash(git diff:*)", "Bash(git log:*)",
              "Bash(git add:*)", "Bash(git commit:*)", "Bash(bd:*)", "Bash(rg:*)", "Bash(ast-grep:*)"],
    "ask":   ["Bash(git push:*)", "Bash(git rebase:*)", "Bash(docker:*)", "Bash(npm publish:*)",
              "Edit(.claude/**)", "Edit(justfile)", "Edit(lefthook.yml)", "Edit(.github/**)"],
    "deny":  ["Read(./.env*)", "Read(./secrets/**)", "Read(~/.ssh/**)", "Read(~/.config/sops/**)",
              "Bash(git push --force:*)", "Bash(rm -rf /*)", "Bash(curl * | sh)"]
  },
  "sandbox": { "enabled": true },
  "hooks": {
    "SessionStart": [{"hooks": [{"type": "command", "command": ".claude/hooks/session-start.sh"}]}],
    "PreToolUse":  [{"matcher": "Edit|Write", "hooks": [{"type": "command", "command": ".claude/hooks/guard-protected.sh"}]}],
    "PostToolUse": [{"matcher": "*", "hooks": [{"type": "command", "command": ".claude/hooks/log-tool.sh"}]}],
    "Stop":        [{"hooks": [{"type": "command", "command": ".claude/hooks/require-evidence.sh"}]}]
  }
}
```
MCP-серверы подключаются только нужные проекту (`.mcp.json`), с минимальными правами; внешний контент (веб, issues, доки) считается недоверенным — инструкции из него не исполняются (защита от prompt injection).

### 12.3 Секреты
- В git — только зашифрованные SOPS+age файлы; ключ age — у человека/в системном keyring, недоступен агенту (`deny Read`).
- Приложение получает секреты при запуске (`sops exec-env secrets.enc.yaml 'just run'`), агент их не видит.
- gitleaks в pre-commit и CI; при утечке — ротация по RUNBOOK.

### 12.4 Журнал действий, ошибок и затрат
- `log-tool.sh` → `.agent-log/YYYY-MM-DD.jsonl`: время, сессия, инструмент, команда/файл, exit code, длительность (без содержимого секретов).
- OpenTelemetry Claude Code (`CLAUDE_CODE_ENABLE_TELEMETRY=1`, OTLP) → self-hosted **Langfuse** или **Phoenix**: токены, стоимость, ошибки инструментов, по сессиям и задачам.
- `ccusage` — ежедневный отчёт о затратах; стоимость записывается в заметки задачи Beads при закрытии.
- Еженедельный разбор: повторяющиеся ошибки → новое правило в AGENTS.md, hook или проверка (так harness улучшается сам).

### 12.5 Действия, требующие решения человека
- `git push` в общие ветки, merge в `main`, теги и релизы, публикация пакетов;
- изменение защищённых файлов (проверки, CI, права агента, hooks), удаление/ослабление тестов;
- принятие ADR, изменение публичных контрактов и ломающие изменения;
- миграции и любые операции с продовыми данными, удаление данных/файлов пользователя (сначала бэкап);
- новые зависимости с сетевым доступом/нативным кодом или несовместимой лицензией (GPL/AGPL в проприетарном коде);
- работа с секретами, доступами, платёжными и внешними аккаунтами;
- превышение бюджета, 3 неудачные попытки, противоречия в требованиях, риск потери данных.

## 13. Проверка самого окружения (evals)

Подробности: `evals/README.md`. Набор из ~12 контрольных задач на фикстурном репозитории с известными ответами.
Прогоняется headless (`claude -p … --max-budget-usd`) после каждого изменения harness и раз в неделю.
Метрики: доля успехов, стоимость, время, число нарушений правил. Результаты — `evals/results.jsonl`, сравнение с прошлым прогоном.

Категории: поиск/навигация, реализация, ревью (заложенные баги), восстановление после прерывания,
честность (задача, которую нельзя решить без ослабления проверки — ожидается эскалация), свежесть документации, параллельная работа.

## 14. Что ещё стоит учесть (дополнения к исходным требованиям)

1. **Шаблон и обновление harness** — Copier-шаблон, чтобы улучшения доезжали во все проекты (`copier update`). Сам harness версионируется.

4. **Prompt injection** — недоверенный контент (веб, issues, логи) обрабатывается subagent без прав на запись и выполнение.
5. **Наблюдаемость приложения** — OpenTelemetry в самом коде, структурированные логи, health-checks: агенту нужно видеть поведение системы, а не только тесты.
6. **Производительность** — бюджеты (время ответа, размер бандла, память — особенно на Spark с общей памятью GPU/CPU), бенчмарки в CI для критичных путей.
7. **Feature flags** — для рискованных изменений, чтобы откат не требовал релиза.
8. **Данные и приватность** — фикстуры без персональных данных, генераторы тестовых данных.
9. **Доступность UI и i18n** — axe-core в Playwright для веб-приложений.
10. **Onboarding** — `just setup` поднимает всё с нуля за одну команду; проверяется в CI на чистом контейнере.

## Решение по предложению 8 (2026-09-24)

Полный eval длительного сопровождения (12–15 доработок × конфигурации × повторы) **отложен**: он не влияет на расход

3. Детерминированные проверки механизмов — `evals/bypass` (без модели); P1/P2/S/R1/C1 — смоук перед крупными изменениями.

   исходники, ломаются на копии mutmut → маркер `source`; проверено в песочнице агента.
