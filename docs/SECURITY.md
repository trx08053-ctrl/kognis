# Безопасность

Правила написания кода и чек-лист ревью. Основа — OWASP Top 10 (2021), OWASP API Security Top 10 (2023),
OWASP ASVS 4 (уровень 2), CWE Top 25. «Авто» — что ловит `just verify`; остальное — ревью по чек-листу.

## Как устроена защита
| Слой | Инструмент | Что ловит |
|---|---|---|
| lint | ruff, правила `S` (bandit) | SQL из строк, `shell=True`, pickle, `yaml.load`, `random` для токенов, md5/sha1, `verify=False`, пароли в коде |
| frontend | Biome, группа security | `dangerouslySetInnerHTML`, `eval`, `target=_blank` без `rel` |
| sast | Semgrep: `security/semgrep.yml` (правила harness) + наборы OWASP | открытый редирект, HTML из строки, секреты в логах, флаги cookie, CORS `*`, JWT без проверки, path traversal, токены в localStorage, переход по адресу из данных |
| deps | osv-scanner (офлайн-база) | известные уязвимости зависимостей (`uv.lock`, `pnpm-lock.yaml`) |
| secrets | gitleaks | ключи и пароли в репозитории |
| tests | `tests/security/test_access.py` (защищён) | маршрут открыт без входа, нет теста доступа к чужому ресурсу (IDOR) |
| stage | Trivy | уязвимости системных пакетов образа (CRITICAL — стоп) |
| CI | OWASP ZAP baseline против staging | заголовки безопасности, флаги cookie, утечки в ответах |
| ревью | reviewer + этот чек-лист; раздел «2c. Угрозы» в TASK | логика доступа, бизнес-правила, всё, что не видно статически |

Подавление находки — только `# nosemgrep: <id>  justified: <task-id> <причина>` (или `noqa`, `biome-ignore`
с тем же обоснованием); ревьюер проверяет каждое. Новая зависимость — решение человека.

## Правила для кода (безопасные умолчания)
1. **Доступ (A01, API1/API5).** Каждый маршрут закрыт по умолчанию; публичный — только из
   `security/public-routes.txt`. Любой запрос к данным фильтруется по владельцу **в запросе к БД**
   (`WHERE owner_id = :user`), а не после загрузки. Чужой объект → 404. Проверка прав — на сервере, не в интерфейсе.
2. **Ввод (A03, API8).** Все входные данные — через схемы Pydantic/TypeScript-типы с ограничениями (длина, диапазон,
   перечисления). SQL — только параметры ORM/`text(...).bindparams`. Никаких `eval`, `exec`, `shell=True`.
3. **Вывод (A03).** HTML — только через шаблоны с автоэкранированием / JSX; без `dangerouslySetInnerHTML`.
   Ошибки наружу — без трассировок, SQL и внутренних путей.
4. **Аутентификация (A07, API2).** Пароли — argon2id/bcrypt; сессия — случайный токен ≥ 32 байт в cookie
   `HttpOnly; SameSite=Lax; Secure` (вне локальной разработки), в БД — только хэш токена; выход удаляет сессию;
   лимит попыток входа; одинаковый ответ «неверный email или пароль».
5. **Секреты (A02).** Только из окружения (`.deploy/<env>.app.env`, `secrets/`), не в коде и не в логах.
   Криптография — стандартные библиотеки (`cryptography`, WebCrypto), AES-GCM, случайные числа — `secrets`.
6. **Логи (A09).** Идентификаторы и события, не содержимое пользовательских данных, не пароли и токены.
7. **Запросы наружу (A10 SSRF).** Адрес — из конфигурации или белого списка, не из ввода пользователя; таймауты.
8. **Заголовки (A05).** CSP без `unsafe-inline`/`unsafe-eval`, `X-Content-Type-Options: nosniff`,
   `frame-ancestors 'none'`, `Referrer-Policy`; HSTS за https. CORS — только перечисленные источники.
9. **Ресурсы (API4).** Лимиты размера тела, длины списков и пагинация; дорогие операции (ИИ, экспорт) — с лимитом.
10. **Зависимости (A06).** Минимум новых пакетов; lockfile; `deps` в verify; обновления — Renovate.

## Раздел «2c. Угрозы» в TASK (обязателен для risky)
Для задач, которые касаются входа, прав, пользовательских данных, файлов, внешних запросов, платежей:
- **Активы:** какие данные/действия защищаем.
- **Кто и как может атаковать:** чужой пользователь (IDOR), аноним, злонамеренный ввод, перебор.
- **Меры и тесты:** каждая угроза → мера → тест (в т.ч. `@pytest.mark.security("idor", "<METHOD> <path>")`).
`just task-done` не закроет risky-задачу без заполненного раздела 2c.
