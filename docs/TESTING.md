# Тестирование

## Уровни (для модульного монолита)
1. **Модуль** — `tests/<модуль>/`: бизнес-правила и сценарии модуля через его публичный API; быстро, без БД/сети
   где позволяет ответственность. `just test-module <модуль>` — во время работы.
2. **Взаимодействие модулей** — тесты модуля-потребителя с реальным публичным API соседа (не моками его внутренностей).
3. **Сквозные сценарии** — tests/e2e/ (`@pytest.mark.e2e`): ключевые пользовательские пути через вход системы.

Тесты проверяют **наблюдаемое поведение и бизнес-правила**; привязка к внутренним вызовам и приватным
функциям — только если без неё никак (тогда объяснить в тесте). Изменение внутренней реализации при том же
поведении не должно требовать переписывать тесты. Исправление дефекта — тест, который падает на прежнем коде:
`just regress tests/<модуль>/test_<баг>.py`.

## Инструменты по уровням
| Уровень | Где | Что проверяет | Запуск |
|---|---|---|---|
| unit + property-based | `tests/test_*.py` | бизнес-логику `domain`, чистые функции; hypothesis для инвариантов | `just test-fast` |
| integration (`@pytest.mark.integration`) | tests/integration/ (создать при появлении) | реальные БД, очереди, HTTP — через testcontainers, без моков инфраструктуры | `just test -m integration` |
| contract | tests/contract/ | реализация соответствует `docs/contracts/` (Schemathesis для OpenAPI, JSON Schema) | `just test -k contract` |
| e2e (`@pytest.mark.e2e`) | tests/e2e/ | 5–15 ключевых пользовательских сценариев (Playwright для веба, CLI через subprocess) | `just test -m e2e` |

`just verify` запускает все уровни. Зависимости для integration/e2e (`testcontainers`, `playwright`,
`schemathesis`) добавляются, когда появляется такой код — `uv add --dev …` требует решения человека.

## Приёмочные сценарии (связь «критерий → проверка»)
Каждый критерий `ACn` из `tasks/<id>/TASK.md` подтверждается тестом, который проверяет **поведение для
пользователя** через публичный интерфейс — HTTP-запрос к поднятому сервису, запуск CLI, действия в браузере
(Playwright), чтение данных после «перезапуска» — а не внутреннюю функцию:

```python
@pytest.mark.acceptance("crm-c02", "AC2")
def test_closed_deal_cannot_move(api_client) -> None: ...
```

`just task-done <id>` отказывает, если у какого-то ACn нет такого теста; сами тесты проходят в `verify`,
поэтому закрытая задача = каждый критерий подтверждён на версии кода из evidence.

## UI-замечания человека (кликом по интерфейсу)
`just ui-feedback <id> [target] [port]` поднимает прокси перед приложением (по умолчанию `http://localhost:5173` →
порт 7777, доступен из локальной сети). Человек открывает приложение через прокси, **Alt + клик** по элементу
(или кнопка «💬 UI») → комментарий. Замечания пишутся в `tasks/<id>/ui-feedback.md` с селектором, текстом,
размером, стилями и фрагментом HTML. Агент исправляет каждое `open`, проверяет на странице, меняет статус на
`done` и дописывает «Сделано: …» — метка на странице становится зелёной. С открытыми замечаниями `task-done`
задачу не закроет.

## Правила
- Тест проверяет поведение через публичный интерфейс, а не детали реализации.
- Тест не повторяет реализацию (property-тест `f(x) == <тело f>` бесполезен) — проверяйте инварианты и примеры из критериев приёмки.
- Ошибка в продакшене → сначала падающий тест, потом исправление.
- Нельзя ослаблять: удалять или смягчать assert, менять ожидаемые значения под код, добавлять skip/xfail без `justified:`.

## Автоматические планки (`scripts/check_ratchet.py`)
- общее покрытие строк ≥ планки из `.quality-baseline.json` (глобальный минимум — 80 %);
- покрытие изменённых строк ≥ 80 % (diff-cover против main);
- число подавлений `justified:` в `src/` и `tests/` не растёт.

После улучшения — `just ratchet-up` (планка только растёт). Понизить — правка `.quality-baseline.json`, защищённый файл, решение человека.

## Мутационное тестирование (по необходимости)
Для критичного ядра `domain`: `uvx mutmut run --paths-to-mutate src/<pkg>/domain` — выжившие мутанты = непроверенное поведение.
