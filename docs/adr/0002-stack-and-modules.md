# 0002. Стек из шаблона и модульный монолит с планируемыми модулями

- **Статус:** Accepted (jusk-one по делегированию, 2026-09-28; см. docs/DECISIONS-NIGHT.md D1–D2)
- **Дата:** 2026-09-28 · **Решили:** агент (ожидает принятия jusk-one) · **Задача:** kognis-b8z

## Контекст
Kognis — дневник с ИИ-анализом, шифрованием и игровой механикой. Нагрузка небольшая, команда малая, требуются
приватность и сменный ИИ-провайдер. Стек задан заказчиком: FastAPI + PostgreSQL + React/TypeScript.

## Варианты
1. **Модульный монолит** (FastAPI, общая БД, модули с публичными API) — просто, транзакции, границы проверяются import-linter.
2. **Микросервисы** — избыточно для нагрузки и команды.
3. **Ничего не делать** — модулей под сценарии нет.

## Решение
Вариант 1. Модули: `users` (есть), затем `diary`, `analysis`, `ai`, `gameplay`, `access` (см. ARCHITECTURE §3).
ИИ — за адаптером `AiProvider`; доступ к функциям — через `access.can_use` (заготовка под тарифы).

## Переход
1. U1: расширить `users` (пароль, вход, сессия), создать `diary` (обычная запись), добавить правила import-linter
   (изменение проверок — решение человека).
2. Остальные модули — отдельными задачами по сценариям U2–U7.

## Проверка результата
Приёмочный тест U1 и `just verify`; пересмотр при появлении требований к независимому масштабированию.

## Последствия
- **Плюсы:** простота, единая транзакционность.
- **Минусы:** общая БД требует дисциплины владения таблицами.
- **Что нужно сделать:** правила import-linter для новых модулей, миграции, карточки модулей.
- **Когда пересмотреть:** нагрузка на ИИ-анализ мешает основному приложению.
