# 0005. Преемственность разборов — сжатая «память» вместо старых записей

- **Статус:** Proposed
- **Дата:** 2026-09-30 · **Решили:** предложено агентом, принять — человеку · **Задача:** kognis-sky

## Контекст
Разбор нового периода должен помнить прошлые, но отправлять старые записи дорого (токены) и лишний раз раскрывает
данные провайдеру.

## Варианты
1. **Память-дайджест** ≤ 2 000 символов + итог прошлого разбора ≤ 1 500 — дёшево, обновляет сама модель; риск дрейфа.
2. **Старые записи в каждом запросе** — точно, но дорого и неограниченно растёт.
3. **Ничего не делать** — нет преемственности.

## Решение
Вариант 1. Модель возвращает `memory` (обновлённый дайджест) и `changes`; сервер хранит дайджест в `analysis_memory`,
показывает пользователю и удаляет по кнопке.

## Переход
Миграция 0015 (expand). Старые разборы работают без новых полей.

## Проверка результата
Тесты сообщений провайдера (AC4); ai-eval с предыдущей памятью — прогон на реальной модели.

## Последствия
- **Плюсы:** запрос ограничен по размеру; пользователь контролирует память.
- **Минусы:** качество дайджеста зависит от модели; дайджест — персональные данные (152-ФЗ), поэтому показывается пользователю и удаляется по кнопке.
- **Когда пересмотреть:** по результатам ai-eval или смене провайдера.
